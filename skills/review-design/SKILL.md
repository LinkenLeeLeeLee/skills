# 人工审核开发设计

优先让审核人理解业务变化、判断关键决定，再核对工程细节。Skill 指导设计判断，JSON 保存结论，Schema 约束数据，Markdown 是同一版本的人工阅读视图；执行 AI 使用这些设计及目标仓库规则。

## S - Scope

- 支持目录预览、完整设计和增量更新；默认后端，不因编写设计修改业务代码或环境。
- 人工文档与 JSON 成对交付。结论维护在 JSON，审核意见先回写 JSON，再生成 Markdown。
- 不代替产品审批、代码 Review 或任务实施；执行时关联现有规格和任务，避免另建一套业务结论。

## C - Constraints

- 开发设计的核心语言使用中文：标题、业务说明、设计取舍、流程说明、审核事项及图表说明均用中文；类名、方法名、API 路径、字段名、枚举值、配置键及需要原样引用的产品文案保留原文。用户明确指定其他语言时按该次要求执行。此项为用户对设计文档的明确语言约定，目标仓库的通用英文文档默认约定不将本设计稿改为英文。
- 结构以 [Schema](assets/development-design.schema.json) 为准，阅读顺序见 [正文模板](assets/development-design-template.md) 与 [功能模板](assets/development-design-feature-template.md)。保留九章；表格列、段落和步骤的展示由渲染器决定，不直接照搬 JSON 字段布局。
- 正式生成或修订前读取 [填写规则](references/filling-guide.md)；数据状态、版本、引用和命令见 [数据与生成约定](references/data-contract.md)。目录预览只读模板。
- 背景与目标用简短文字说明为什么改、达到什么结果；业务主线用一句执行链串起全文。详细结果矩阵放业务规则，操作节点与事务边界放功能设计，范围细节放对象边界。复杂功能先说明执行顺序，技术定位跟随对应步骤。
- 功能正文统一按“功能说明、处理流程、规则约束”阅读，使用四字加粗标签，不再展开多级编号。入口及确认状态归功能说明，主要步骤归处理流程，状态、异常和副作用归规则约束；实现步骤和时序图集中在“实现细节”折叠区，未决问题在正文集中展示。
- 九章主标题使用两字或四字中文短语，章编号用“一、二、……”；二级标题用“4.1、4.2……”等阿拉伯数字层级编号，目录与正文一致。审核目录只列九章和独立功能，不展开字段区域或每个功能的六项内部结构。保留显式锚点及返回目录，新增功能后自动重建导航。
- 正文聚焦业务变化、架构变更、关键决定、核心流程、失败／事务边界及业务验收。架构的变更前后、模块职责、依赖方向和核心调用图必须直接可见；组件明细、实现步骤、时序、模型字段和 UT／集成测试清单可展开阅读。精简目录不能隐藏影响方案判断的内容，真正阻塞实施的问题必须在正文可见。
- 区分已确认要求、当前实现、设计建议和待确认方案。功能开头用“方案定位”指出会影响实现的未决事项；相关流程、图、接口、资源和验收沿用同一确认状态。源码已有行为不等于用户已批准。
- 首页只提炼需要审核人作决定的关键问题；环境事实放对应配置区域，阻塞整体方案的事实问题仍前置。填写状态只用于完整性管理；不适用原因保留在 JSON，正式视图省略无关区域和空表。
- 业务变化比较基线和源码实现基线分别说明；工程清单使用一致的比较口径。环境资源列出所需配置及实际核实状态，不凭源码断言环境已存在。
- 各区域与功能使用从 1 开始的普通数字编号。结构化关联使用“区域＋编号”；视图生成短名称和链接。编号引用绑定设计版本，不能把旧稿行号直接套到新稿。
- 同一决定在所属区域详细定义，概览只提炼业务后果并链接。既有 Markdown 与 JSON 冲突时核对最新用户决定与证据；只有旧 Markdown 时先迁移并保留原稿。
- 架构比较以需求实施前的基线为起点，另记已实施源码的快照；功能分支已有实现不能据此判定本需求没有架构变化。正文用简短对照说明模块职责和依赖如何变化，有变化时展示现状与目标核心调用图；确实无变化时说明原因并保留一张核心图。历史基线不明时标待核实，不虚构旧架构。绘图使用可用的 [module-callgraph](../module-callgraph/SKILL.md)；不可用时明确说明并遵循相同样式。
- 有状态、多步骤、跨模块或外部副作用的关键流程提供包含主要失败分支及提交边界的时序图。简单功能按适用内容展示，不为填模板增加图或抽象层。
- 目标仓库约定优先于通用示例。按实际边界选择生命周期、模型、API、持久化和配置等专项 Skill；不引入不存在的类、基础字段或机制。
- 单元测试聚焦核心行为及独立风险，优先复用，不按方法、字段组合或覆盖率机械扩张。遵守用户的 Review／验证顺序，数据校验不代替人工批准。

## P - Process

1. 读取已有设计、需求、用户决定和相关工程依据，确定本次是内容修订还是源码刷新；表达修订保留原核对日期，不伪装成重新查证。
2. 明确业务变化及源码基线，先写业务主线、关键结果与范围。新设计从空白 JSON 初始化；更新时增加设计版本，Schema 升级按数据约定处理。
3. 确定规则、对象边界及各功能的方案定位，再组织架构和执行流程；同步 API、数据、配置与验收。对未决方案写明影响和关闭条件。
4. 汇总本次审核事项，关联具体功能或记录；功能的关联需求用于生成阅读导航。完整性依靠数据，阅读顺序由模板和渲染器承担。
5. 按授权生成同版本 JSON／Markdown。结构与引用检查、文档展示检查、源码核对、运行验证分别报告；先 Review 后验证时先提供可审核草稿。

## V - Verification

- 授权后检查 Schema、状态、编号和引用；送审不保留待填写，不适用有原因，待确认有问题、影响和关闭条件。
- 审核人能从概览理解行为，沿功能导航找到契约和验收；长流程有顺序，字段按模型或表分组，引用可定位。
- 需求有设计与验收落点；正常状态、空表和通用填写提示不干扰正文。分组展示仍保留每字段的必填、适用接口、来源、限制及兼容语义。
- 对同一未决决定，检查功能定位、流程、图和验收是否一致；结构通过不证明语义正确或足以实施。
- 按影响核对模块、模型、授权、事务、并发、幂等及副作用；不将建议或原稿证据写成当前已核实事实。
- 检查实际 Markdown 与 Mermaid 展示；未渲染时说明范围。生成脚本不验证 Mermaid 语法或图中业务关系。

## O - Output

- 目录预览：展示阅读顺序和区域，不虚构设计。
- 完整设计／更新：同目录同名 `design.json` 与 `design.md`，沿用用户指定位置；说明版本、关键调整、待确认项和实际验证情况。
- 本地稿更新保留已存在结论，默认不覆盖无关文件；不主动提交、推送、部署或发送审核消息。按工作区要求在必要验证后暂存本次文件。
