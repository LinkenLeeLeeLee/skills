# 后端设计填写规则

本文件供 Skill 决策使用，不复制到生成的审核文档。字段结构以 Schema 为准；模板规定阅读顺序，渲染器选择适合人的段落、步骤、表格和链接。

## 通用规则

- 从 `development-design.blank.json` 复制设计数据，逐区填充。禁止直接改空白模板或 Schema 来容纳单次需求。
- 区分现状、已确认要求／决定、设计建议、待确认。源码、需求材料与运行证据不可互相替代；在相应说明、确认状态及参考资料中写明依据。
- 各表及功能使用普通数字编号，从 1 连续递增，禁止 R、BR、F、API、DB、CFG、AC 等前缀。结构化引用使用“区域＋编号”，引用数组可包含多个目标；引用显示为章节名和数字编号。
- `状态` 仅表示区域是否已填写，不表示业务确认或测试通过。`说明` 保存正文结论；不适用必须写原因；待确认必须记录问题、影响及关闭条件。草稿允许待填写，送审不允许待填写；已知结论与未决问题可以在待确认区域同时保留。
- 说明文字可以使用段落、列表和代码示例，但不能用标题重建目录，也不能把应填表的数据全部塞入说明。图放入 Mermaid 字段，只存源码，不包含代码围栏。
- 一个决定只详细定义一处，其他位置引用。编号在所属区域内唯一；“已填写”不代表已审核、已实现或已验证。
- 文档信息分别填写需求比较基线、源码基线和验证状态；源码基线区分实施前的比较版本与已核对的实现快照。默认按同一比较版本标注新增／修改／复用；已有文档若保留相对实现快照的剩余工作清单，必须在该区域说明范围，不能与本需求整体变更混读。分支已有实现不等于本需求没有变化。
- 文档修辞调整沿用原证据及核对日期；只有重新读取拥有方源码或环境后才更新查证结论。实际环境未知时记录核实事项，不断言资源已新增或已存在。
- 审核关注点可区分设计决定、事实核实和重点复核，关联具体功能或记录。首页优先放需要作出决定的少量问题，事实核实归对应区域，避免把每一项实现检查都列作人工审批。
- 待确认方案在功能开头和每处相关流程、图、接口、资源、验收中标明条件。保留已经确认的原则，不因一个局部问题把整个功能都改为未知。

## 1. 背景 & 目标

背景与目标默认用简短的“背景／目标”两项说明问题及业务效果，业务主线用一句执行链串起全文，并链接关键章节。详细结果矩阵放第 2 章业务规则，触发节点与事务边界放第 4 章对应功能，范围细节放对象边界；不在开头重复解释整套方案。

本次审核关注点置于业务主线之后，每项用简短问题链接详细依据和影响。当前行为附可复查依据，不能把拟议方案描述为现状；完整性状态和生成过程不放进业务叙述。

## 2. 需求改动点

- 功能改动清单只描述增加、调整或取消的业务能力及可观察结果，不展开类、接口或存储实现。
- 业务规则说明触发条件、限制、计算口径、优先级和拒绝结果；关联对应的需求记录。
- 对象范围与权限边界明确业务对象、交易／版本／明细粒度、历史范围、租户归属和共享规则，以及谁可以对哪些数据执行什么操作。页面仅作为业务入口，按钮展示不能代替后端授权。

## 3. 架构设计

- 架构变更是正文审核内容。用简短对照说明变更前后、受影响模块的职责与依赖、关键事务边界；核心调用图直接展示，不能因精简标题而整章折叠。组件和模型明细可作为技术参考。
- 核对实施前的比较版本和目标实现快照。架构有修改时，现状与目标调用关系分图，包含核心调用方向、模块及必要的分层边界、跨模块契约；只有相对实施前也确实无变化时，才说明复用关系并省略目标图。未取得历史基线时明确证据缺口，不能把已实现的功能分支当作旧架构。
- 使用可用的 module-callgraph Skill，遵守当前版本的节点归属、变更配色和边语义。图前正文说明绿色新增、橙色修改、蓝色复用及比较版本；纯现状图蓝色表示现状，不绘制图例节点。区分直接调用、SPI 分派和接口实现；未核实的关系标待确认，拟新增节点和调用明确标拟议，已实施差异不写成尚未实施。
- 区分业务模块、构建子模块与技术层，不把三者平铺为同一层。以实际构建与源码核实归属。
- 针对 saas-service：Adapter 负责入口适配及安全声明；Application 负责用例、授权与事务；Domain Service／DO 承担业务规则、状态及写入；Domain 定义 Repository／Gateway 契约，Infrastructure 实现技术细节；跨模块同步能力通过提供方 Client，说明其实现所在层。简单只读查询遵循当前仓库允许的例外，不机械增加层。
- 对象清单区分 DO、VO、Enum、HTTP Cmd／Qry／DTO、Client 模型与 PO，说明对象身份、版本、归属、核心行为及模型转换边界。存量 models／shared-models 沿用实际边界，不能为了模板迁移。PO 不泄漏到其他层或模块；Converter 不承载查询、权限或业务规则。
- 不单列“关键设计取舍”表。影响实施的结论、限制和待确认问题写在对应架构或功能中。

## 4. 功能点设计

- 按独立业务能力增加功能实例；JSON 保留六个子区域，正文只为功能本身建立标题。内部统一为“功能说明、处理流程、规则约束”三个四字加粗标签，不生成 4.x.x 审核标题。入口与方案定位归功能说明；状态、异常、并发和副作用归规则约束。无关区域省略，原因留在数据；简单功能不为每个按钮另拆实例。
- 每个功能填写结构化关联需求及方案定位。方案定位区分已确认原则、原稿／当前实现和待决定部分；不把“部分实施”当作唯一实施说明。
- 入口列明参与者、前置条件及关联需求／规则／边界。HTTP、Client、事件、Job 等入口分别承担自身授权契约，不默认继承其他入口的安全保护。
- 主流程的说明用简短编号步骤表达处理顺序；互斥入口或分支明确区分，不能画成依次执行。正文说明关键结果和提交边界；详细步骤与时序图集中在一个“实现细节”折叠区，输入、输出、组件及失败处理随步骤保留。所有区域的待确认问题在本功能规则约束末尾集中展示，重复问题只展示一次。
- 状态表在人工视图合并为“编号、操作与条件、状态变化、处理结果”四列，保留原状态、目标状态、角色条件、副作用和重复请求结果；不以缩列为由丢失状态或幂等语义。
- 区分本地事务与跨模块／远程动作，不假定远程结果会随本地事务回滚。状态表区分业务状态、交易状态和内部执行状态。
- 有状态、多步骤、跨模块或外部副作用的关键流程提供 Mermaid 时序图，包含主要拒绝／失败分支、提交边界及副作用时机。普通字段变更不强制画图。
- 异常、并发与幂等说明重复请求、超时、冲突及部分失败的结果；使用锁时明确对象、拥有者和释放／恢复条件，不因模板默认新增锁。
- 审计与外部副作用说明操作者、时间、原因和关联标识，明确事件、工作流、财务、再保、文件、通知等适用动作的提交顺序、失败及补偿。
- 查询在主流程中说明行粒度、筛选、分页、总数、稳定排序、空结果、权限及历史版本范围。

## 5. API 接口设计

- HTTP API 清单在人工视图中只显示“编号、变更方式、方法与路径、用途”四列。调用方、权限、对应功能和兼容处理仍保留在 JSON，供实施及结构化关联使用，不在该表另加列。
- 分别定义 HTTP、跨模块 Client、事件与异步契约；路径、方法、枚举和消息标识以源码为依据，拟新增明确标建议。
- HTTP 区分入口身份／应用／租户准入与对象数据授权；Client 明确提供方、调用方、模型归属、可信租户／身份来源、双方权限责任和空值语义。
- 事件说明发布方、消费入口、载荷版本及重复／乱序约定。流程、投递失败与补偿在功能章节定义，注册／启用配置在第 7 章。
- 请求与响应逐个契约定义完整字段路径、类型、格式、必填／可空、来源及兼容规则。明确可修改字段，服务端身份、租户、状态和审计值不能由请求随意覆盖。复杂模型可在说明中附与字段一致的 JSON 示例。
- 人工视图按请求／响应模型分组，组前列适用契约；只有适用范围不同的字段再单独标注。内部仍保留逐字段契约关联，不把仅更新必填的字段展示成创建也必填。
- 查询说明筛选、排序、分页等契约。错误表区分 HTTP、Client 和事件的实际失败形式，不统一假设为 HTTP 错误码；操作项展示不能替代执行校验。

## 6. 数据库变更

- 表总览说明职责、关系及历史影响；字段表逐表记录业务字段及项目实际采用的主键、租户、审计、版本／逻辑删除字段，不机械新增。
- 人工视图按表分组；通用更新与审计规则可集中说明，单个字段仍保留例外和准确约束。省略重复文字不等于省略数据语义。
- 索引和约束对应具体查询、唯一性或幂等规则，明确租户与逻辑删除影响、分页排序及数据量。
- 迁移说明脚本链路、读取兼容、回填来源、执行顺序和失败恢复，区分建议与已执行变更。多表事务以功能设计为准。

## 7. 配置变更

- 分 Master Table／Record、Trigger Event、Message Resource 和其他配置填写；配置字段应精确到键、语言、占位参数、原值与新值、范围及管理方式。
- Trigger Event 引用功能中的触发时机和接口章节的事件契约；本区域只定义环境注册、启用等配置变化。
- 说明维护权限、配置缺失行为、环境差异、生效机制、依赖顺序及配置回退；敏感信息只写来源与用途。
- saas-service 所属工作区环境初始化必须遵守实际规则；Message Resource 禁止通过 Liquibase、changelog、changeSet 或其中 SQL 增删改，填写实际消息资源管理方式。
- 涉及产品或业务配置时，检查实际需要的发布版本、导入导出和主子对象管理链路，不自行引入新机制。

## 8. 测试与验收

- 分别检查独立规则、真实组件协作和业务结果。每项需求有验证安排，按风险选层，不在三层重复所有场景；明确真实依赖和替身，设计阶段只写计划，执行结果必须有真实证据。
- 单元测试先判断核心功能与风险。核心业务判断、关键状态变化、金额／计算规则和重要异常分支需要单元测试；仅协议转发、简单字段映射、文案或配置调整且不含核心逻辑时不单独新增，并说明理由。
- 用最小充分的用例验证核心行为，优先复用或调整已有测试，同一规则优先参数化。不按方法、字段、条件组合或覆盖率机械增加用例，不重复框架已有测试；新增用例对应独立规则或未覆盖风险。仅在规则变化、发现缺陷或出现未覆盖关键风险时继续扩展，防止无限膨胀。这些要求由 Skill 执行，不复制到模板正文。
- 集成测试按实际风险覆盖授权与租户隔离、读写、事务回滚、Client、事件、并发、重试、部分失败及历史兼容；替身成功不等于真实集成通过。
- 验收场景明确业务角色、对象／版本／状态、动作及可观察结果。入口可以是接口或人工操作，不默认必须通过页面。

## 9. 参考资料

记录需求材料、确认决定、当前源码及运行证据的具体来源和版本。源码尽量到类／方法，不能用整个仓库链接证明具体行为。来源不可访问时说明缺口，不伪造事实。
