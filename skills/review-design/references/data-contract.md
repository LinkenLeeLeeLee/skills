# 数据与生成约定

## 文件职责

| 文件 | 职责 |
|---|---|
| `assets/development-design.schema.json` | JSON Schema Draft 2020-12；固定对象、字段、记录列、状态及结构化引用类型 |
| `assets/development-design.blank.json` | 结构完整的空白数据；区域初始状态为待填写，无示例业务结论 |
| `assets/development-design-template.md` | 固定九章及各区域占位符；不包含填写指导 |
| `assets/development-design-feature-template.md` | 功能说明、处理流程、规则约束及可展开的实现细节；对应原有六个数据区域 |
| `references/filling-guide.md` | 需求、源码、工程边界和测试范围的判断规则，供 Skill 使用 |
| `scripts/design_document.py` | 初始化、数据校验及生成入口 |
| `scripts/review_view.py` | 人工阅读视图：短链接、顺序步骤、分组字段及适用内容展示 |

交付时 `design.json` 是设计结论的唯一维护源，`design.md` 是同一版本的人工视图。JSON 使用 UTF-8，不包含注释或重复键。当前 Schema 版本为 `3.0.0`；`design_revision` 从 1 递增，不能把 Schema 版本当作设计版本。

2.0.0 相对 1.0.0 增加必填的文档信息“需求比较基线／验证状态”、背景中的“业务主线与关键结果”、审核记录的“类型／关联内容”，以及每个功能的“方案定位／关联需求”。从旧版升级须保留原稿并根据真实材料补齐这些内容，不能只替换版本号或自动推断确认结论。

3.0.0 移除“架构设计.关键设计取舍”区域及其引用目标，不再单列方案对比表。升级时将该区域独有且仍有效的结论、限制和未决事项归入对应架构或功能，重定向实际存在的引用，再删除旧区域、更新版本并重新生成。旧 Schema 数据由版本检查拒绝。

## 区域结构

所有内容区域均有 `状态`、`说明` 和 `待确认问题`。表格区域增加 `记录` 数组；图区域增加 `Mermaid` 源码字段。纯说明区域也保持固定对象结构，不允许以一个任意对象替代整个章节。

| 状态 | 条件 | 送审模式 |
|---|---|---|
| 待填写 | 初始化状态，可以逐步补充数据 | 拒绝 |
| 已填写 | 纯说明区域有非空说明；表格区域至少一条记录；无待确认问题 | 允许，仍需审核业务内容 |
| 不适用 | 有非空原因；表格记录为空、图源码为空、无待确认问题 | 允许 |
| 待确认 | 至少一个非空的问题、影响、关闭条件；可同时保留已知说明、记录和图 | 允许，明确保留未决结论 |

功能集合的记录字段名为 `功能`；已填写时至少一个功能，其他状态规则相同。每个功能的六个区域仍分别填充状态；方案定位说明确认边界，关联需求用于生成导航。整个功能集合不适用时不创建虚构功能。

审核关注点的类型为设计决定、事实核实或重点复核，关联内容引用功能或记录。局部待确认问题仍在所属区域定义；关注点只提炼审核问题和导航，不维护另一份决定。

图区域的已填写要求有说明，Mermaid 可为空；是否需要图由 Skill 根据架构／流程变化判断，不能把没有图等同于通过设计审核。

送审数据的标题和所有文档信息必须非空。空白数据的草稿／未实施是初始元信息，不代表已有人确认需求。按实际情况修改元信息，无法确认的基线或作者等必须明确说明，禁止编造。

## 编号与关联

- 每个表格和功能列表独立使用 `1、2、3……`，顺序与编号一致；不添加字母前缀。字段定义等跨表记录用“表／实体”列明确归属。
- 功能数量决定 `4.1、4.2……`；功能名称来自 JSON。六个数据区域保留，视图整理为功能说明、处理流程、规则约束，内部用四字加粗标签，不新增目录层级；实现步骤及图集中展开，不适用原因只保留在数据中，原区域锚点仍保留。
- `关联需求`、`对应功能`、`契约编号`、`关联规则及章节`、`关联需求及章节`是结构化引用数组，例如：

```json
[
  {"区域": "需求改动点.功能改动清单", "编号": 1}
]
```

- `区域` 取值限定为 Schema 列出的表格路径或 `功能点设计`；编号必须真实存在。需求字段只能指向功能改动清单，功能字段只能指向功能列表，契约字段只能指向 HTTP／Client／事件清单。
- 同一需求可以关联多个规则、功能或验收；脚本检查结构化引用的目标存在和上述字段类型。它不校验自由文本里的引用，也不自动证明需求覆盖完整。
- 自由文本中的关联写具体章节及数字编号，例如“2.2 第 1 项”，不要只写不明确的“1”。结构化引用自动渲染为短名称与文内链接，JSON 保留完整区域路径；引用编号只在同一设计版本内定位，不是跨版本稳定身份。

## 说明、表格与图

说明可使用段落、列表、紧凑业务对照表、链接和代码示例；不新增标题。代码围栏必须闭合。具体字段仍存入对应记录，概览提炼业务结果；不能把所有结构化数据转移到说明中。

正常的已填写状态不展示；待填写在草稿中提示，待确认展示问题、影响和关闭条件。不适用在数据中保留原因，视图省略无关内容及空表。主流程概述留在正文，详细记录在技术参考中按编号生成步骤，保留输入、处理、输出、组件及失败边界。

功能视图把入口、方案定位及需求关联放入“功能说明”，主流程说明放入“处理流程”；状态、异常与副作用归“规则约束”。六个区域的待确认问题在规则约束末尾集中显示，内容相同的问题只显示一次，时序图中的问题也不能仅藏在折叠区。状态表合并为四列，保留所有原字段语义；JSON 与 Schema 结构不变。

请求／响应按模型分组，组前展示适用契约，范围不同的字段单独标注；数据库字段按表分组。显示列可以合并相关信息，字段语义、必填、可空、来源、兼容和历史规则必须保留。其他记录使用对应表格展示，换行、HTML 和竖线转义。人工视图的列不必与 JSON 属性逐项相同。

HTTP API 清单固定展示“编号、变更方式、方法与路径、用途”四列。其余契约属性保留在 JSON，不从数据中删除；此项是展示调整，Schema 版本不变。

Mermaid 只存源代码，不含 Markdown 围栏；渲染器负责加围栏，不验证图形语法或运行逻辑。用户数据中的 `{{...}}` 不再执行二次模板替换。

审核关注点、每个表格和每个图保留固定数据区域。业务概览先于审核事项；第 4 章导航根据功能关联需求和业务验收记录生成。链接存在不代表覆盖充分，仍需核对业务含义。空白 JSON 不能作为完整设计交付。

正文模板的 `{{目录}}` 是生成器占位符，不是 JSON 字段。一级章节使用“一、需求背景”等中文编号，二级标题使用“4.1 产品选择规则维护”等数字编号，目录同步采用相同格式。审核目录只列九章及独立功能，移除完整字段目录；锚点继续使用 `section-1`、`section-4-1` 等数字形式以支持既有引用，每章可返回目录。代码围栏内的示例标题不进入目录。源数据中的字面 `{{目录}}` 不会被二次替换。

`{{参考:区域路径}}` 显示区域名称与内容，不生成独立审核标题，并省略不适用区域；是否折叠由模板中的 `<details>` 决定。架构变更对照、模块分工、核心调用图、关键决定、未决问题和业务验收留在正文；组件与模型明细、接口字段、索引及测试明细按需展开。架构的比较版本与实现快照写入文档信息，不能因目标已在分支实现而把目标调用关系标为不适用。此项仅调整视图及填写规则，Schema 及完整 JSON 数据结构保持不变。

## 使用命令

以下示例从 Skill 目录运行，输出目录需事先存在。脚本要求 Python 3.9+；初始化只用标准库，校验与生成依赖 `jsonschema`。缺依赖时在选定 Python 环境安装，不自动变更系统环境：

```sh
python3 -m pip install -r scripts/requirements.txt
python3 scripts/design_document.py init /path/to/change/design.json
```

按 Schema 与填写规则编辑 `design.json`，然后选择当前阶段的命令：

```sh
# 草稿结构校验与预览，允许待填写
python3 scripts/design_document.py validate /path/to/change/design.json --draft
python3 scripts/design_document.py render /path/to/change/design.json /path/to/change/design.md --draft

# 送审：不允许待填写，允许有完整问题说明的待确认区域
python3 scripts/design_document.py validate /path/to/change/design.json
python3 scripts/design_document.py render /path/to/change/design.json /path/to/change/design.md
```

默认不覆盖现有输出。更新同一生成视图时可追加 `--overwrite`；不能用 Markdown 输出覆盖输入 JSON，也不能输出到 Skill 资源目录。脚本只读源数据、不修改审核状态或版本号、不自动生成审核通过结论。

工作区要求先 Review 后验证时，遵守该顺序，不因本文件列出命令而提前执行。

## 维护与验证

修改结构时同步更新 Schema、空白 JSON、展示模板、填写规则及相关脚本／测试；版本不匹配直接拒绝，不自动猜测旧数据的新含义。不提供旧自由文本 Markdown 的自动迁移。正常 `render` 命令先做结构校验，再生成文档；生成器自身修改的审核预览不应被宣称为结构或回归检查通过。

获得验证授权后运行：

```sh
python3 -m unittest discover -s tests -p 'test_*.py'
```

重点检查错误输入被拒绝、数据引用可定位、待确认不会被掩盖、功能重复结构与 Markdown 输出一致，以及默认不覆盖源数据或既有文件。
