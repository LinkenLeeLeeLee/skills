# 模块调用关系图

从已确认的源码版本追踪业务调用，画出带模块归属、调用方向和方法语义的流程图。

## S - Scope

- 用户询问当前架构、某个类的调用方、跨模块引用，或要求按 `gi-policy.application` 等格式标注类的归属时使用。
- 可分析 TransAttach，也可用明确的业务类或入口作为其他主题的搜索起点。
- 开发设计包含架构变更时，可在核实的现状图之外绘制独立的目标设计图；只提供调用关系表达，不替代业务设计决定。
- 只分析和绘图时不引入重构。用户另行要求修改代码时，再按当前仓库的 Rules 和适用实施 Skill 执行。

## C - Constraints

- `模块.子模块` 由实际 Gradle 工程目录确认。例如 `gi-policy/gi-policy-application` 标为 `gi-policy.application`；Java package 单独记录。不能从 `com.bytesforce.client.claim` 推断它一定属于 `claim`，该包也可能来自 `claim-config.client`。
- 图描述一个明确版本。工作区、主目录、MR 分支不一致时分别说明，不能把两个版本的类拼成一张“当前架构”图。查询不会自动授权 pull、merge、切换分支、修改代码或推送。
- 普通箭头表示已核实的方法调用；接口指向实现用虚线并标“实现”。继承、SPI 查找、字段取值回调、数据读取分别标注，不能用 import 或字段注入直接证明调用。
- 运行时协作图和 Gradle 编译依赖图分别绘制。业务模块之间双向协作，不等同于存在编译依赖环，也不能据此声称 Spring 装配成功。
- 本次合并、删除及复用的类以当前源码为准。历史设计和参考图只是搜索线索，不能把目标设计、旧类或测试替身画成当前生产实现。

### 绘图样式

- 默认使用 `flowchart TB`。架构变更分为“现状调用关系”和“目标调用关系”两图；现状只画源码已核实关系，目标图说明相对现状的变化。没有架构变更时不机械补目标图。
- 每个类节点采用 `模块.子模块<br/>类名`；拟新增类另加 `<br/>【拟新增】`，未定类名用职责节点并明确“拟新增职责”，不冒充生产声明。目标图按业务模块使用 subgraph 分组，调用链过长时按配置维护、运行同步等职责分图。
- 已有组件使用浅蓝色，拟新增组件使用浅绿色；拟修改的已有组件仍用蓝色并在节点或配套表注明修改点。颜色之外保留文字标记，不能只靠颜色传达状态。配色使用下列 classDef，仅声明图中实际使用的样式。

```text
    classDef existing fill:#eef4ff,stroke:#5376aa,color:#182f50
    classDef added fill:#e6f6eb,stroke:#388653,color:#174c2b
```

- 在图内放置独立的“图例”，优先位于右上角，用同色样例注明“绿色＝新增”“蓝色＝现状”。新增／现状以图前说明的源码基线为准，不代表功能是否验证通过。图例节点不连接业务调用边，也不需要模块标签；仅含现状组件的图只列“蓝色＝现状”。Mermaid 自动布局无法保证固定角落，必要时调整布局；未查看渲染结果时不声称已位于右上角。
- 现状图实线标实际调用方法；目标图尚未实施的调用边写“拟调用／拟扩展：用途”，不虚构方法已存在。接口到实现始终使用虚线并标“实现”，不得把虚线统一解释为待确认。继承、SPI、回调等关系分别注明语义；未决关系写清“待确认”，必要时移到图外问题表。
- 图前说明源码基线及图例，图后用简短职责表解释模块分工、核心变化和未展开边界。不把整个持久化链、DTO 或所有类塞进核心图；辅助流程按需要补图。图中省略的设计仍须在正文有落点。

## P - Process

1. 定位源码：读取当前路径、`git status --short --branch`、`git log -1 --oneline`，必要时用 `git worktree list --porcelain` 找到相关工作区。用户给了 MR 时使用可用的连接工具或 GitLab 页面核对分支；无法访问时说明本地分析的版本范围，不把本地提交当成 MR 已更新。
2. 用 `rg --files` 找业务类和 `build.gradle`，用 `rg -n` 找调用。候选多时执行本 Skill 的 `scripts/inventory_sources.py ROOT '关键词正则'`，一次取得文件路径、类名、Java package 和模块归属。脚本只列候选，不自动判定调用边。
3. 读取核心方法正文，向上追踪业务入口，向下追踪 Client 契约 → 提供方实现 → Domain Service/Provider → Repository。规则引擎等回调业务模块的分支要继续追到业务对象解析和字段取值，不能停在 Client。
4. 分开记录配置维护、页面只读查询、业务动作校验、规则执行/业务回调；按当前问题选用相关视图。对各边记录调用方法、调用行号、条件及结果用途，区分“返回缺失项”和“抛错阻断流程”。
5. 生成 Mermaid 图。每个类节点写成 `模块.子模块<br/>类名`；接口及实现有助理解边界时都保留。节点太多时分图，辅助 DTO、Converter 和 Enum 可放补充表。表格可增加真实 Java package、职责和源码链接。
6. 说明哪些能力复用了既有业务服务，哪些逻辑仍由公共服务或引擎承担。若用户要求修改架构，实施后重跑搜索并重画受影响视图，删除旧节点和引用，保持职责、事务、权限与失败语义的说明准确。

## V - Verification

- 现状图的每个类节点都能定位到本次版本中的生产声明，每条调用边都能定位到实际调用语句。目标图中的已有组件遵循同一证据要求，拟新增组件与拟议调用明确标注，不能被当作已实现事实。
- 调用方清单包含不带主题前缀的类。例如附件检查的调用方可能叫 `AcceptanceServiceImpl` 或 `GiPolicyQuoteServiceImpl`。
- 核对接口实现、继承和 SPI 分派。条件执行调用 Provider 取值，并不表示它再次进入完整业务规则执行。
- 确认同名包所属模块，核对 `build.gradle` 的实际使用者依赖。分析编译关系时才绘制编译依赖图。
- 检查 Mermaid 围栏、节点 ID、引号、箭头类型和模块标签。未用渲染器查看时只声称已做语法/结构检查。
- 核对现状／目标分图、模块分组、蓝绿配色、图内颜色图例及文字标记是否一致；渲染后确认图例位置尽量靠右上角且不干扰业务图。接口虚线必须标“实现”，拟议调用与正文设计相符。
- 只读分析无需启动服务或运行业务测试；源码关系不能当作运行时调用次数、功能验收或 Spring 无循环依赖的证据。

## O - Output

- 开头标明源码工作区、分支或提交，以及相邻工作区存在的关键版本差异。
- 给出模块职责表，以及回答当前问题的架构图/流程图；图中所有类都标 `模块.子模块`。
- 解释关键分支、复用边界和是否阻断业务；给出少量可点击的绝对路径源码证据。
- 用户要求保存时写入指定位置；未指定时直接在回复展示，避免自动改业务仓库或提交。使用本 Skill 本身不授权 Git 或外部发布操作。
